# Решения

## 2026-11-19 — каркас приложения

FSD не используем. Экрана два, фичи две, отдельных слоёв entities/widgets/processes это не окупает.

Бэкенд — слои FastAPI в `backend/app`: `api` (HTTP), `services` (Keitaro и сценарии), `domain` (чистые правила, в первую очередь веса), `models` (SQLAlchemy), `schemas` (Pydantic). Настройки в `config.py`, SQLite в `db.py` (`sqlite:///./app.db`). Локальная база нужна, чтобы помнить офферы, снятые в Keitaro: в интерфейсе они остаются с 0% и кнопкой Bring Back.

Фронтенд — `frontend/src`: `app` (Mantine и роутер), `pages` (список кампаний `/`, офферы `/campaigns/:id`), `features/create-campaign`, `features/edit-offers`, `shared/api` (fetch, без axios).

Библиотеки, которые берём сейчас:

- Бэкенд: FastAPI, uvicorn, SQLAlchemy 2, pydantic-settings, httpx, pytest.
- Фронтенд: Vite 5, React 18, TypeScript, react-router-dom, Mantine (`core`, `hooks`, `form`), Vitest, Testing Library, jsdom.

Mantine закрывает кнопки, таблицу, модалку и поля одной лёгкой библиотекой. Ant Design и MUI тяжелее, своего набора компонентов под три виджета не собираем.

Пока не подключаем axios, TanStack Query, zod, Redux и Tailwind. ESLint пришёл из шаблона Vite, отдельно его не выбирали.

`build/` и `*.egg-info` в `.gitignore`: это следы установки пакета, не исходники.

## 2026-11-20 — пересчёт весов

Ключ Keitaro лежит в `backend/.env` как `KEITARO_API_KEY`. Файл в `.gitignore`, в репозиторий не попадает. `Settings` читает его из этого файла, независимо от рабочей папки. `backend/.env.example` повторяет остальные переменные и оставляет ключ пустым.

Панель трекера — `KEITARO_ADMIN_URL` (`https://tlgk.host/admin`). Вызовы Admin API — `KEITARO_API_URL` (`https://tlgk.host/admin_api/v1`), заголовок `Api-Key`.

Домен, группа и источник кампании фиксированы и лежат в `backend/.env` уже как id, не только как имена: домен `kylovoa.com` — `1813`, группа кампаний `FORTESTS` — `10332`, источник `FORTESTS` — `836`. Перед созданием кампании их всё равно сверяем со списками Keitaro: id мог измениться.

## 2026-11-20 — создание кампании

`POST /campaigns` принимает `name`, `geo`, `offer_id`. К имени без префикса дописывается `test_shvirev_`, уже готовое имя не удваивается. Alias — итоговое имя в нижнем регистре, пробелы заменяются на `_`.

`GET /campaigns` возвращает только кампании с этим префиксом.

Перед записью сверяем домен, группу (`GET /groups?type=campaigns`), источник и оффер. Кампания создаётся с `type=position` и id из настроек. Первый поток `geo` — regular, редирект на `https://www.google.com`, фильтр страны. Второй поток `offer` — regular, схема landings, выбранный оффер со share 100. Тесты ходят в фейковый клиент, не в трекер.

Первый экран — список и модалка создания. Палитра с фото: фон `#D8EDF4`, текст `#5A5058`, вторичный `#918980`, границы `#B8ADAC`, кнопка `#D28E5F`. Строка кампании — обычный `tr`: ссылка вместо строки рисуется как `<a>` и склеивает записи в одну линию. Клик по строке открывает `/campaigns/:id`.

Поле оффера — строка из цифр без кнопок шага. Через 300 мс `GET /offers?q=` фильтрует офферы Keitaro: подстрока в id или в имени. Список — выпадающий слой поверх модалки, не выше 240px, с прокруткой. Пока запрос идёт, в правой части поля крутится индикатор. Выбор подставляет в поле одну строку «id — name» и закрывает список. Если строку стёрли, таймер и текущий запрос отменяются, старый ответ не показывается.

Правило живёт в `app.domain.weights.distribute_shares`. Тесты пишем до реализации.

Редактор офферов читает `GET /campaigns/{id}/streams` и пишет только `POST /campaigns/{id}/push`. Поток без офферов есть в ответе и не превращается в строки. Поток с офферами отдаёт id, имя и share. Снятый оффер, которого уже нет в Keitaro, остаётся со share 0 и `removed`. Первое чтение запоминает офферы потока в SQLite и в Keitaro ничего не пишет. Если активный оффер из базы пропал из потока, ответ оставляет его с долей 0, сразу пересчитывает доли живых и отдаёт `external_change` со старыми долями. Повторное открытие снова видит это расхождение, пока не было push. Если в базе оффер уже `removed`, это не чужое удаление и доли не пересчитываются. До push клиент Keitaro записей не получает. Push один раз отправляет пересчитанные доли только живых офферов: снятого в массиве `offers` нет.

В `backend/app/mocks/keitaro.json` список `remove_offers`. Команда `python -m app.mocks.remove_marked_offers` из каталога backend просит запущенный мок снять эти id со всех потоков. В файл и в SQLite она не пишет. Страницу кампании нужно открыть до команды, чтобы офферы уже были запомнены, и обновить после.

Пока трекер недоступен, `KEITARO_MOCK=true` в `backend/.env` подменяет клиент. Сид лежит в `backend/app/mocks/keitaro.json`: домен, группа, источник, офферы и кампании. Потоки кампании лежат в `streams_by_campaign`. Мок один на процесс, созданные кампании и новые доли живут до перезапуска и в файл не записываются. Запомненные офферы мока лежат в `backend/app.mock.db`, обычный режим — в `backend/app.db`. При остановке процесса бэкенда мок-файл удаляется, обычный остаётся.

На экране офферов заголовок — имя из `GET /campaigns`. Потоки — отдельные секции на фоне страницы, правится только поток со строками офферов. Поиск нового оффера открывается Popover от кнопки в шапке этого потока. Булавка, которая не меняет доли, не делает таблицу грязной и в Keitaro не уходит, пока не изменится доля. Грязь таблицы — это отличие долей от последнего сохранённого состояния: удалили оффер и вернули его, и доли те же — таблица снова чистая. Снятие оффера по-прежнему грязное, пока доли не совпали. Подписи кнопок русские: «Вернуть», «Отмена», «В Keitaro», булавка без текста.

Список и экран офферов не лежат на белой карточке. Фон страницы белый, шапка и таблица стоят на нём, под шапкой линия. Голубой фон с фото не используем: он спорит с тёплым текстом и кнопкой. Карточка остаётся у модалки создания и у поиска оффера. Со страницы офферов на список ведёт короткая ссылка «Компании» со стрелкой: линия при наведении идёт и под стрелкой, и под словом. У «Вернуть» закруглённая стрелка, у «Удалить» корзина.

Доли — целые проценты, сумма активных стремится к 100. Снятый оффер (`removed`) получает 0 и в дележе не участвует, даже если был запинен. Запиненный и не снятый сохраняет свой процент. Остальные делят `100 − сумма запиненных`. Остаток от деления раздаётся по одному проценту сверху вниз: при 23 на четверых выходит 6, 6, 6, 5, а не 8, 5, 5, 5. Если запиненные в сумме больше 100 — `ValueError`. Один только запиненный оффер остаётся со своим процентом, до 100 его не растягиваем. Снятый запиненный не резервирует вес, но его процент хранится в `pinned_share`. Пока он снят, в таблице 0%. «Вернуть» отдаёт в делёж тот же процент.
